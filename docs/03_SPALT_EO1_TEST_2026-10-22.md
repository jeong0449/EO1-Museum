# spalt/EO1 원본 앱 빌드 및 EO1 실기 검증

**실험일:** 2026-10-22  
**프로젝트:** EO1-Museum  
**대상 기기:** Electric Objects EO1  
**참조 프로젝트:** spalt/EO1  
**문서 상태:** 실험 기록 / EO1 Gallery 개발 방향 결정

---

## 1. 실험의 배경

EO1-Museum의 현재 안정 버전(v1)은 Electric Objects EO1의 Android 4.4.2 위에서 Firefox를 실행하고, PC의 로컬 HTTP 서버가 제공하는 전시 이미지를 표시하는 구조이다.

부팅 시에는 별도로 제작한 MetBoot가 `BOOT_COMPLETED`를 받아 Firefox를 실행하며, Firefox의 시작 페이지가 PC의 EO1-Museum 서버를 가리키도록 설정되어 있다.

현재 안정적으로 동작하는 구조는 다음과 같다.

    Android boot
        ↓
    MetBoot
        ↓
    Firefox
        ↓
    PC local HTTP server
        ↓
    EO1-Museum web slideshow

이 방식은 안정적이고 이미 실사용이 가능하지만 다음과 같은 의존성이 있다.

- EO1과 PC가 같은 네트워크에 연결되어 있어야 한다.
- PC에서 EO1-Museum HTTP 서버가 실행되어 있어야 한다.
- EO1에서 Firefox가 실행되어야 한다.
- 최종적으로 EO1 단독으로 동작하는 장치라고 보기는 어렵다.

따라서 다음 단계에서는 PC의 웹 서버와 Firefox에 의존하지 않고, EO1 내부 저장공간에 전시 이미지를 저장한 뒤 Android 네이티브 앱이 직접 슬라이드쇼를 실행하는 독립형 구성을 목표로 하였다.

## 2. 최초 EO1 Gallery 개발 시도

처음에는 Android Studio의 최신 템플릿으로 새로운 프로젝트를 만들었다.

프로젝트 이름은 다음과 같이 정하였다.

    App name: EO1 Gallery
    Package: com.eo1museum.gallery
    Version: 0.1

EO1은 Android 4.4.2이므로 최소 SDK를 API 19로 낮추었다.

    minSdk = 19

Gradle Sync 자체는 성공하였다.

최신 템플릿의 `MainActivity`에는 다음과 같은 AndroidX 코드가 포함되어 있었다.

    AppCompatActivity
    EdgeToEdge
    ViewCompat
    WindowInsetsCompat
    ConstraintLayout
    Material

EO1 Gallery에는 이러한 현대적인 UI framework가 필요하지 않으므로 `android.app.Activity`와 `ImageView`만 사용하는 매우 단순한 구조로 바꾸려고 하였다.

그러나 프로젝트를 빌드하자 다음 오류가 발생하였다.

    Cannot fit requested classes in a single dex file
    (# methods: 68499 > 65536)

단순히 그림을 표시하는 앱임에도 AndroidX/AppCompat/Material 등의 의존성 때문에 고전적인 Android DEX 65,536 method 제한을 넘어선 것이다.

의존성을 제거하고 순수 Android API만 사용하는 방법도 시도할 수 있었지만, 최신 Android Studio/Gradle 환경을 2013년의 Android 4.4.2에 맞추기 위해 계속 역방향으로 조정하는 것은 불필요하게 복잡하다고 판단하였다.

이 시점에서 개발 전략을 변경하였다.

## 3. spalt/EO1을 기반으로 사용하기로 한 이유

라는 방향으로 전환하였다.

## 4. spalt/EO1 최초 Gradle Sync 실패

GitHub에서 `spalt/EO1` 프로젝트를 다운로드하여 Android Studio에서 열었다.

그러나 최초 Gradle Sync는 다음 오류와 함께 실패하였다.

    Unable to find method
    'org.gradle.api.artifacts.Dependency
     org.gradle.api.artifacts.dsl.DependencyHandler.module(java.lang.Object)'

Android Studio는 다음과 같은 일반적인 가능성을 제시하였다.

- Gradle dependency cache 손상
- Gradle daemon 손상
- third-party plugin incompatibility

그러나 프로젝트 디렉터리를 직접 살펴보면서 더 근본적인 문제가 발견되었다.

프로젝트 루트에는 다음 파일이 있었다.

    gradlew
    gradlew.bat

그러나 일반적인 Gradle Wrapper에 있어야 할 다음 디렉터리가 없었다.

    gradle/
    └── wrapper/
        ├── gradle-wrapper.jar
        └── gradle-wrapper.properties

즉 Gradle Wrapper 실행 스크립트는 존재하지만 실제 wrapper 설정이 빠져 있는 불완전한 상태였다.

## 5. Android Gradle Plugin 버전 확인

프로젝트의 최상위 `build.gradle`을 확인하였다.

내용은 매우 단순하였다.

    // Top-level build file where you can add configuration options common to all sub-projects/modules.
    plugins {
        id 'com.android.application' version '7.4.1' apply false
        id 'com.android.library' version '7.4.1' apply false
    }

따라서 이 프로젝트는 Android Gradle Plugin 7.4.1을 사용하도록 작성되어 있음을 확인하였다.

최신 Android Studio의 최신 Gradle/JVM 조합을 그대로 사용하는 대신 다음과 같은 비교적 당시 환경에 가까운 조합을 복원하기로 하였다.

    JVM 17
      ↓
    Gradle 7.5
      ↓
    Android Gradle Plugin 7.4.1
      ↓
    spalt/EO1

## 6. Gradle Wrapper 복구

앞서 새로 만들었던 `EO1_Gallery` 프로젝트에는 정상적인 Gradle Wrapper 디렉터리가 존재하였다.

    gradle/
    └── wrapper/
        ├── gradle-wrapper.jar
        └── gradle-wrapper.properties

이 `gradle` 디렉터리를 `spalt/EO1` 프로젝트로 복사하였다.

그 후 `gradle-wrapper.properties`에서 Gradle distribution URL을 다음과 같이 수정하였다.

    distributionUrl=https\://services.gradle.org/distributions/gradle-7.5-bin.zip

---

## 7. Gradle checksum 오류

처음 Sync를 시도하자 Gradle distribution 검증 오류가 발생하였다.

    Verification of Gradle distribution failed!

    Expected checksum:
    bbaeb2fef8710818cf0e261201dab964c572f92b942812df0c3620d62a529a01

    Actual checksum:
    cb87f222c5585bd46838ad4db78463a5c5f3d336e5e2b98dc7c0c586527351c2

이는 다운로드한 Gradle 7.5 파일이 변조되었다는 의미라기보다, `EO1_Gallery`의 최신 Gradle Wrapper 설정에서 복사된 다른 Gradle 버전용 `distributionSha256Sum` 값이 그대로 남아 있었기 때문이었다.

실험 단계에서는 `gradle-wrapper.properties`에서 해당 `distributionSha256Sum` 줄을 제거하였다.

Gradle distribution URL은 공식 Gradle 서버를 그대로 사용하였다.

    distributionUrl=https\://services.gradle.org/distributions/gradle-7.5-bin.zip

---

## 8. JVM 버전 문제

Gradle 7.5를 지정한 뒤 Android Studio는 다음 문제를 보고하였다.

    Gradle 7.5 is not compatible with JVM 25.

현재 Android Studio의 최신 runtime인 JVM 25는 Gradle 7.5와 호환되지 않았다.

Android Studio는 `Use JVM 17`을 제안하였다.

이를 선택하여 Gradle JVM을 Java 17로 변경하였다.

최종적으로 다음 환경이 구성되었다.

    JVM 17
      ↓
    Gradle 7.5
      ↓
    Android Gradle Plugin 7.4.1
      ↓
    spalt/EO1

이 상태에서 **Gradle Sync가 성공하였다.**

Android Studio는 AGP 7.4.1이 오래된 버전이므로 Upgrade Assistant를 사용할 것을 제안했지만 이를 실행하지 않았다.

이 프로젝트의 목적은 최신 Android 기능을 사용하는 것이 아니라 Android 4.4.2 기반 EO1에서 안정적으로 실행하는 것이므로, 정상 작동하는 구형 빌드 환경을 의도적으로 유지하기로 하였다.

## 9. 원본 프로젝트 빌드

Gradle Sync 성공 후 Android Studio에서 다음 메뉴를 실행하였다.

    Build → Assemble Project

결과:

    BUILD SUCCESSFUL

따라서 `spalt/EO1` 원본 소스를 기능적으로 수정하지 않은 상태에서 현재 개발 PC의 Android Studio 환경으로 정상 빌드할 수 있음을 확인하였다.

생성된 주 APK는 다음 위치에서 확인하였다.

    app/
    └── build/
        └── outputs/
            └── apk/
                └── debug/
                    └── app-debug.apk

프로젝트에는 `app-partner` 모듈도 존재하지만 이번 실기 시험에서는 `app` 모듈의 `app-debug.apk`를 사용하였다.

## 10. EO1과 ADB 연결

EO1의 전원을 켜고 PC와 micro-USB 케이블로 직접 연결하였다.

Windows PowerShell에서 다음 명령을 실행하였다.

    .\adb.exe devices

결과:

    List of devices attached
    115343222       device
    emulator-5562   offline

EO1의 serial은 다음과 같다.

    115343222

상태가 `device`로 표시되므로 ADB 연결은 정상이다.

이 PC는 이전 ADBApprovalHelper 실험에서 이미 EO1의 RSA debugging 승인을 받은 상태이므로 별도의 RSA 승인 과정 없이 바로 ADB 연결이 가능하였다.

`emulator-5562 offline`은 이번 실험과 관계가 없으므로 무시하였다.

## 11. APK 설치

다른 ADB 장치와 혼동하지 않도록 EO1 serial을 명시하여 APK를 설치하였다.

    .\adb.exe -s 115343222 install "...\app-debug.apk"

Windows 탐색기에서 `app-debug.apk`를 PowerShell 창으로 드래그하면 전체 파일 경로가 자동으로 입력되는 방법을 사용하였다.

설치 결과:

    Success

즉 현재 빌드한 `spalt/EO1` APK가 실제 EO1의 Android 4.4.2에 정상적으로 설치되었다.

## 12. 설치된 패키지 확인

설치 후 다음 명령으로 EO1 관련 패키지를 확인하였다.

    .\adb.exe -s 115343222 shell pm list packages | findstr eo1

결과:

    package:com.dan.eo1
    package:com.eo1.adbapprovalhelper

각 패키지는 다음과 같다.

    com.dan.eo1
        → 이번에 설치한 spalt/EO1

    com.eo1.adbapprovalhelper
        → 이전에 제작한 ADB RSA 승인 보조 앱

## 13. spalt/EO1 수동 실행

Activity 이름을 직접 지정하지 않고 Launcher activity를 실행하기 위해 Android의 `monkey` 명령을 사용하였다.

    .\adb.exe -s 115343222 shell monkey -p com.dan.eo1 -c android.intent.category.LAUNCHER 1

실행 결과 EO1 화면에 **Flickr User ID와 API key를 입력하는 초기 설정 화면**이 정상적으로 표시되었다.

이 결과는 매우 중요하다.

단순히 APK가 설치된 것뿐 아니라 다음 사항을 실제 EO1에서 확인한 것이다.

    APK 설치 성공
        ↓
    Activity 실행 성공
        ↓
    EO1 화면 제어 성공
        ↓
    초기 설정 UI 표시 성공

즉 spalt/EO1의 Android 코드가 현재 보유한 EO1의 Android 4.4.2에서도 실제로 실행된다.

이번 실험에서는 Flickr User ID와 API key를 입력하여 Flickr 이미지 다운로드까지 시험하지 않았다.

EO1-Museum의 최종 구조에서는 Flickr를 사용하지 않을 계획이므로 Flickr 통신 성공 여부는 이번 실험의 필수 조건이 아니다.

## 14. Flickr 기능의 의미

spalt/EO1은 Flickr를 이미지 공급원으로 사용한다.

일반적인 사용 구조는 다음과 같다.

    사용자의 사진/작품
        ↓
    Flickr
        ↓
    Flickr API
        ↓
    spalt/EO1
        ↓
    EO1 display

따라서 초기 화면에서 Flickr User ID와 API key를 요구한다.

EO1-Museum에서 원하는 구조는 이와 다르다.

    The Met 등 공개 미술관 데이터
        ↓
    PC에서 수집 및 선별
        ↓
    EO1-Museum/images
        ↓
    ADB push
        ↓
    EO1 internal storage
        ↓
    EO1 Gallery

따라서 향후 EO1 Gallery에서는 Flickr 관련 기능을 제거하고 로컬 이미지 표시 기능으로 대체할 예정이다.

## 15. 재부팅 시험

spalt/EO1 설치 및 실행 후 EO1의 전원을 완전히 내렸다가 다시 켰다.

이 시험의 목적은 다음 두 가지였다.

1. spalt/EO1 설치가 기존 EO1 환경을 손상시키지 않았는가?
2. spalt/EO1의 Home/Launcher 기능이 실제 EO1에서도 작동하는가?

재부팅 후 Android는 다음과 같은 화면을 표시하였다.

    Select a home app:

    Electric Objects
    EO1

여기서:

    Electric Objects
        → EO1의 기존 원본 Home 앱

    EO1
        → 새로 설치한 spalt/EO1 앱

이다.

즉 spalt/EO1의 Manifest에 구현된 `HOME` category가 실제 EO1에서도 정확하게 작동한다는 것을 확인하였다.

Firefox가 Home 앱 목록에 나타나지 않는 것은 정상이다. Firefox는 일반 Android application이지 Home/Launcher application이 아니기 때문이다.

## 16. 기존 EO1 환경으로 복귀

기존 환경을 유지하기 위해 Home 앱 선택 화면에서 다음을 선택하였다.

    Electric Objects

그 결과 EO1은 원래 Electric Objects Home 환경으로 정상 복귀하였다.

따라서 이번 실험을 통해 다음 사실도 확인하였다.

- spalt/EO1은 기존 Electric Objects Home과 공존할 수 있다.
- APK 설치만으로 EO1 firmware나 eMMC 시스템이 변경되는 것은 아니다.
- 필요하면 원래 Home으로 안전하게 돌아갈 수 있다.
- spalt/EO1을 Home replacement로 사용할 가능성도 실제로 존재한다.

기존 EO1-Museum v1의 MetBoot/Firefox 구성 역시 별도로 보존되어 있다.

## 18. 이번 실험에서 확인된 핵심 사실

### 18.1 spalt/EO1은 단순한 참고 코드가 아니다

이번 실험 전까지 `spalt/EO1`은 EO1용으로 작성된 과거의 공개 소스라는 의미가 컸다.

그러나 이번 실험으로 다음이 모두 직접 확인되었다.

    source
      ↓
    Gradle Sync
      ↓
    Build
      ↓
    APK
      ↓
    ADB install
      ↓
    actual EO1
      ↓
    successful execution

따라서 spalt/EO1은 **현재 보유한 실제 EO1에서 작동하는 것이 검증된 코드베이스**이다.

### 18.2 최신 Android 프로젝트를 API 19로 후퇴시키는 것보다 유리하다

최신 Android Studio 템플릿에는 기본적으로 다음과 같은 현대적인 구성 요소가 따라온다.

    AndroidX
    AppCompat
    Material
    ConstraintLayout
    EdgeToEdge
    WindowInsets

이를 Android 4.4.2/API 19에 맞추어 하나씩 제거하거나 구버전으로 맞추는 것은 가능하지만 불필요한 복잡성을 만든다.

반면 spalt/EO1은 애초에 EO1을 대상으로 만들어졌으며 EO1 특화 로직이 이미 존재한다.

따라서 다음 접근법이 더 합리적이라고 판단하였다.

    최신 Android 앱
          ↓
    API 19로 억지로 후퇴

보다

    실제 EO1에서 작동하는 앱
          ↓
    불필요한 기능 제거
          ↓
    EO1 Gallery로 단순화

하는 것이 낫다.

### 18.3 Home replacement 기능도 실제로 검증되었다

spalt/EO1 설치 후 재부팅하자 Android가 다음 두 Home 앱을 표시하였다.

    Electric Objects
    EO1

따라서 향후 EO1 Gallery가 충분히 안정화되면 Firefox나 MetBoot를 거치지 않고 **EO1 Gallery 자체를 Home 앱으로 사용하는 완전 독립형 구성**도 현실적으로 가능하다.

다만 이 기능은 초기 v0.1에서 바로 적용하지 않는다.

우선 내부 저장공간의 이미지 슬라이드쇼가 안정적으로 동작하는 것을 확인한 뒤 Home replacement를 적용하는 것이 안전하다.

## 22. 향후 다시 활용할 수 있는 spalt/EO1 기능

EO1 Gallery의 기본 슬라이드쇼가 안정화되면 다음 기능은 단계적으로 재사용할 가치가 있다.

### 자동 밝기

EO1의 ambient light sensor를 이용하여 주변 밝기에 따라 화면 밝기를 조절한다.

### Quiet hours

야간에 화면을 자동으로 어둡게 하거나 끄는 기능은 실제 디지털 액자로 사용할 때 유용하다.

### EO1 하드웨어 버튼

spalt/EO1에는 EO1의 하드웨어 버튼을 처리하는 코드가 있으므로 향후 수동 화면 제어에 활용할 수 있다.

### Home/Launcher replacement

이번 실험으로 실제 작동이 확인되었다.

EO1 Gallery가 충분히 안정화되면 최종적으로 다음 구조를 만들 수 있다.

    Power ON
       ↓
    Android boot
       ↓
    EO1 Gallery as HOME
       ↓
    internal storage
       ↓
    automatic slideshow

이 단계에 도달하면 MetBoot와 Firefox가 더 이상 필요하지 않다.

### 원격 전시 관리

향후 필요하면 Wi-Fi를 통해 새로운 전시 이미지나 metadata를 전송하는 기능을 추가할 수 있다.

그러나 이것은 v0.1 이후의 문제이다.

## 24. 이번 실험의 의미

이번 실험은 단순히 APK 하나를 빌드해 본 것이 아니다.

EO1-Museum 개발에서 다음 중요한 선택을 가능하게 하였다.

첫째, EO1의 기존 Android 4.4.2 환경을 유지하면서도 네이티브 앱 개발이 가능하다는 것을 확인하였다.

둘째, Linux 설치나 kernel 교체와 같은 깊은 시스템 변경 없이도 충분히 독립적인 EO1을 만들 수 있는 가능성을 확인하였다.

셋째, `spalt/EO1`이라는 실제 EO1용 코드베이스가 현재 보유한 EO1에서도 여전히 작동한다는 것을 확인하였다.

넷째, Home/Launcher replacement까지 실제로 동작하므로 최종적으로 EO1 Gallery가 부팅 직후 실행되는 전용 전시 앱이 될 가능성을 확인하였다.

다섯째, 기존 Electric Objects Home으로 안전하게 복귀할 수 있음을 확인함으로써 실험의 위험도도 낮출 수 있었다.

> **EO1 Gallery를 최신 Android 프로젝트에서 억지로 Android 4.4.2에 맞추기보다, 실제 EO1에서 작동하는 것이 확인된 spalt/EO1을 기반으로 단순화하여 개발한다.**

다음 개발 단계에서는 오늘의 빌드 성공 상태를 먼저 보존한다.

그 후 별도의 작업본을 만들어 Flickr 중심 구조를 제거하고 다음 경로의 로컬 이미지를 직접 표시하도록 수정한다.

    /sdcard/EO1-Museum/images/

첫 번째 성공 기준은 매우 단순하다.

> **EO1 내부 저장공간에 넣은 그림 한 장을 EO1 Gallery가 네트워크 없이 전체화면으로 표시한다.**

그것이 성공하면 여러 이미지 슬라이드쇼, 자동 밝기, quiet hours, Home/Launcher replacement 순으로 기능을 확장한다.

이번 실험으로 EO1-Museum은 기존 PC/Firefox 기반 v1을 안전하게 보존하면서도, **PC·브라우저·원래 Electric Objects 서비스에 의존하지 않는 독립형 네이티브 디지털 미술관**으로 발전할 현실적인 경로를 확보하였다.
